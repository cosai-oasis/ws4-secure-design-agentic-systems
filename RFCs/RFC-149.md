# Agent Manifest: verifiable declarations of agent deployment content

**Author:** Imran Siddique (@imran-siddique), OPAQUE Systems  
**Status:** Proposed scope for WS4 review; not an approved specification  
**Originating issue:** [#149](https://github.com/cosai-oasis/ws4-secure-design-agentic-systems/issues/149)

## Summary

Develop a vendor-neutral description of the deployment content an agent is
declared to use, together with the evidence a relying party needs to evaluate
that declaration. The work would define how a signed manifest identifies a
particular revision of that content and how credentials and runtime evidence
can refer to it without conflating their separate claims.

This RFC proposes a work scope. Acceptance would establish that scope and the
workstream's review path. It would not adopt an external specification, approve
a reference implementation, or establish conformance. Specification text,
implementation contributions, and conformance material would receive separate
review against this RFC.

## Problem and intended users

A deployment reviewer needs to identify the content covered by an approval:
for example, software, model references, instructions, policy, tool definitions,
and available data snapshots. A gateway or other relying party needs to connect
that declaration to the agent instance presenting a credential. An investigator
needs to distinguish the declared deployment from evidence of what ran later.

Those questions require different evidence. A valid signature can establish
integrity and signer attribution under a verifier's trust policy. It does not
by itself establish that the signer may approve a deployment, that a running
instance uses the declared content, or that a later action was authorized.

The work would address substitution of declared content, ambiguous references,
unauthorized or stale declarations, and confusion between deployment approval
and runtime observation. It would state what evidence each check consumes and
what remains unknown when evidence is missing.

## Scope

- Define the declaration's subject, revision, issuer, intended use, and time
  boundary. Distinguish content available before execution from later runtime
  artifacts, including decision traces and dynamically created delegation.
- Identify which agent-specific content needs binding, and which existing
  inventory or provenance formats can be referenced. Evaluate reuse before
  defining new fields; the ten-artifact list in the original proposal is input
  to this review rather than an adopted requirement.
- Define requirements for unambiguous content references, signature coverage,
  authorized signers, revocation, freshness, and version changes. Concrete
  serialization and cryptographic profiles would be reviewed separately.
- Describe how a relying party correlates a declaration with a credential and
  with independently evaluated runtime evidence. Cover configuration changes,
  proxies, gateways, and other components that can alter effective behavior.
- Separate content-integrity results, signer authorization, evidence freshness,
  and runtime-binding results. Specify the limits of partial verification.

The first specification proposal would include a threat model identifying the
trusted parties, possible compromised parties, observation boundaries, and
residual risks. Hardware binding would need evidence that connects the actual
measurement subject to the declared content; a container digest and a platform
launch measurement would not be treated as interchangeable.

The following is a proposed division of responsibilities for joint review in
[#209](https://github.com/cosai-oasis/ws4-secure-design-agentic-systems/discussions/209).

| Work | Relationship to this RFC | Boundary to resolve together |
|---|---|---|
| [Agent Credentials #99](https://github.com/cosai-oasis/ws4-secure-design-agentic-systems/issues/99) | Classifies claims, credential formats, and credential use cases. A credential could carry a reference to a specific manifest revision. | Meaning of that claim; subject and instance correlation; independent acceptance of credential and manifest issuers; freshness and revocation. |
| [ODIS contributor draft](https://github.com/cosai-oasis/ws4-odis/blob/148dc4187139a41325e3c6d6e7533d956bd33144/RFCs/ODIS.md) | Its Passport, Bridge, and Router layers address software/runtime identity, delegation, and discovery/governance. A manifest could supply deployment-content evidence consumed by those flows. | Overlap with the registration record and Passport; what a manifest reference establishes; which component verifies runtime binding and which makes an access decision. |
| Inventory and build provenance | Evaluate references to existing BOM formats and provenance statements, including CycloneDX, SPDX, and SLSA. | Which agent-specific facts remain uncovered, and how referenced evidence binds to the same content revision. |
| Runtime and action evidence | Later records could identify the deployment declaration against which observations are evaluated. Coordinate with WS4 provenance work and [evidence-sufficiency proposal #189](https://github.com/cosai-oasis/ws4-secure-design-agentic-systems/issues/189). | Declared versus observed state, observation completeness, and what links a decision to an effect. A deployment declaration alone answers none of these runtime questions. |

For example, a credential might reference deployment revision D. The relying
party would still need to accept both issuers under its trust policy, verify
the referenced content, and evaluate whatever evidence links the running
instance to D. Permission to perform an operation remains a separate decision.
This example proposes a relationship, not a credential schema or an ODIS
extension.

## Non-goals

- Define a replacement identity system, credential envelope, delegation
  protocol, authorization engine, or runtime monitor.
- Claim that a signed declaration proves safe behavior, complete observation,
  successful execution, or legal compliance.
- Import external hardware profiles, platform support claims, conformance
  levels, registries, or governance arrangements by reference.
- Select mandatory hardware platforms or equate software inventory with
  hardware-attested execution. Any proposed assurance profiles need separate
  requirements, limitations, and supporting evidence.
- Contribute TRACE or an external implementation through acceptance of this RFC.

## Proposed work and review

1. Agree the scope and the Manifest/Credentials/ODIS crosswalk. Imran Siddique
   is the proposed lead for this RFC; Ian Molloy has offered to help draft it
   and take the ODIS crosswalk in his [review request](https://github.com/cosai-oasis/ws4-secure-design-agentic-systems/issues/149#issuecomment-5805211443).
   Additional leads and the participation needed for acceptance remain for
   WS4 to confirm.
2. Submit the threat model, reuse analysis, and proposed specification as
   separately reviewable contributions referencing this RFC. Each contribution
   names its lead and identifies the decisions it asks WS4 to make.
3. Review implementation and conformance contributions against the accepted
   specification revision. Require explicit coverage and non-coverage before
   accepting claims based on those contributions.

The WS4 leads and TSC retain their review and acceptance roles. The issue
history records prior proposals and feedback; the accepted RFC revision would
be the authoritative statement of this work's scope. Changes to that scope
would return through review.

## Priority and level of effort

**Proposed priority: P1.** The scope affects how adjacent credential and
provenance work refer to agent deployment content.

**Estimated effort: Large.** The crosswalk, threat model, and specification
review require contributions across those work areas. This RFC sets no delivery
deadline or implementation commitment.

## Drawbacks and alternatives

A separate manifest can duplicate software inventory and credential claims,
introduce another issuer trust decision, and create freshness or privacy risks
when declarations disclose sensitive deployment details. The reuse analysis
and disclosure requirements should address those costs before a new format
is chosen.

Alternatives include defining only a profile of existing inventory/provenance
formats, extending the credential work with deployment-content claims, or
limiting the output to integration guidance. The crosswalk should determine
whether a distinct manifest format is justified.

## Unresolved questions

- Which deployment-review and relying-party use cases should drive the first
  specification, and which organizations will contribute to them?
- What agent-specific content cannot already be represented by referenced
  inventory and provenance formats?
- How should credential issuers, manifest signers, and runtime evidence
  issuers establish the trust and subject relationships needed by a verifier?
- What requires a new declaration revision, and what belongs in a later
  runtime record? How are drift and intermediaries represented?
- Which assurance claims need hardware evidence, and what evidence would be
  sufficient for each proposed profile?
