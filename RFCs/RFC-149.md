# Agent deployment content as a profile of the ODIS Agent Registration Record

**Author:** Imran Siddique (@imran-siddique), OPAQUE Systems

**Status:** Proposed scope for WS4 review; not an approved specification

**Originating issue:** [#149](https://github.com/cosai-oasis/ws4-secure-design-agentic-systems/issues/149)

## Summary

Define how an agent's deployment content (software, model references,
instructions, policy, and tool definitions) is declared in the ODIS Agent
Registration Record, and how a relying party checks it. On the 2026-10-07 WS4
call the group agreed that the registration record is the single source of
truth and that a standalone Agent Manifest is deprecated. This RFC therefore
scopes a named profile and a set of typed references on that record, not a
separate document.

Acceptance would establish the scope of the work. Changes to ODIS text,
profile text, implementations, and conformance material would each need
separate review. No external specification or implementation is being
submitted for adoption through this RFC.

## Problem and intended users

A deployment reviewer needs to identify the content covered by an approval:
software, model references, instructions, policy, tool definitions, and
available data snapshots. A gateway or other relying party needs to connect
that approval to the agent instance presenting a credential. An investigator
needs to distinguish the approved deployment from evidence of what ran later.

ODIS §6.1 already carries the governance half of this: who registered the
agent, who owns it, its lifecycle state, and which runtime issuers it trusts.
It does not yet carry the content half with enough precision to check. The
field mapping in [ws4-odis#35](https://github.com/cosai-oasis/ws4-odis/pull/35)
shows the gaps: `approved_software_refs` is an untyped list, `policy_profile_ref`
is a string with no digest or enforcement mode, and the record has no field for
the reference values a verifier appraises evidence against.

A valid signature on the record establishes integrity and signer attribution
under a verifier's trust policy. It does not by itself establish that the
signer may approve a deployment, that a running instance uses the approved
content, or that a later action was authorized. Each proposed check needs to
state its evidence and what remains unknown when that evidence is missing.

## Scope

- Define typed entries for `approved_software_refs`: each with a reference
  type, a digest, and a named digest input. Candidate types are software
  artifact, provenance, SBOM, source bundle, model, tool catalog, prompt, and
  composition. Decide whether the type registry lives in ODIS core or in the
  profile.
- Define the profile that carries deployment content §6.1 has no field for:
  RAG corpus binding with scan results bound to the scanned subject, memory
  baselines and their checkpoint protocol, audit-chain commitments, human
  oversight declarations, and regulatory declarations. Content that changes on
  its own schedule must be able to advance without a new record version.
- Propose the §6.1 changes the profile depends on, as separate ODIS
  contributions: `policy_profile_ref` as an object carrying digest and
  enforcement mode; a place for verifier reference values and required
  evidence per relationship; who may update a record; and a profile extension
  point the registration schema accepts.
- Define how the Layer 2 verifier appraises runtime evidence against the
  record's reference values, and what it reports per relationship
  (`instance_to_software`, `instance_to_key`) when evidence is missing or
  unverifiable. Hardware launch binding names the composition it binds, so an
  ownership change does not invalidate a running instance.
- Separate content-integrity results, signer authorization, evidence
  freshness, and runtime-binding results. Specify the limits of partial
  verification.

The first profile proposal would include a threat model identifying the
trusted parties, possible compromised parties, observation boundaries, and
residual risks. A container digest and a platform launch measurement would
not be treated as interchangeable.

## Non-goals

- Define a standalone manifest format alongside the registration record.
- Define a replacement identity system, credential envelope, delegation
  protocol, authorization engine, or runtime monitor.
- Claim that a signed record proves safe behavior, complete observation,
  successful execution, or legal compliance.
- Select mandatory hardware platforms or equate software inventory with
  hardware-attested execution. Any assurance profile needs separate
  requirements, limitations, and supporting evidence.
- Contribute TRACE or an external implementation through acceptance of this
  RFC.

## Priority and level of effort

**Proposed priority: P1.** The profile determines how credential, provenance
and runtime evidence work refer to agent deployment content.

**Estimated effort: Large.** The §6.1 changes, the profile, and its threat model
require contributions across those work areas. This RFC sets no delivery
deadline or implementation commitment.

## Drawbacks and alternatives

Putting deployment content in the registration record means every content
change is a record change. The profile has to keep fast-moving content (data
snapshots, memory, audit checkpoints) out of the record version, and the
superseded-version rule in ws4-odis#16 has to hold when only ownership changes.

The alternative the group set aside on 2026-10-07 was a separate manifest
referenced from the record. It duplicated the record's identity and lifecycle
fields and added another issuer trust decision.

## Unresolved questions

- Does `policy_profile_ref` become an object carrying digest and enforcement
  mode?
- Is the typed-reference registry defined in ODIS core or in the profile?
- Do verifier reference values get a §6.1 field, or live only in the profile?
- Should §6.1 name who may update a record?
- Does hardware launch binding target the composition digest rather than the
  record digest?
- For cA2A convergence on §6.3, are hops peer-signed or issued by a Layer 2
  authority, and does child expiry nest or intersect?
