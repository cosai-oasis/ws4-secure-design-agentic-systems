### 3. Behavioral monitoring rework, PR **#220** (8 min)

**What changed (November 3):**

- **Detection and alerting only.** The control raises an alert with its evidence. Deciding the response, and any restriction, halt or quarantine, is now out of scope. Requirement 4 is now an alert when monitoring fails. Ian's fail-closed default moves to the response and enforcement controls.
- **Why response is a separate layer.** A control that can stop an agent must meet the reference monitor properties (containment paper §5.1). Alerts are probabilistic, while responses are policy. The Risk Map already splits detection from response (`controlThreatDetection` and `controlIncidentResponseManagement`). The RFC now lists the existing controls that could carry out a response. The best fit for quarantine is `controlAgentInventoryManagement`, which already has a `suspended` state with credential revocation.
- **OpenShell removed.** The earlier draft cited NVIDIA OpenShell as existing practice. That was an oversight. OpenShell is a good way to check that kernel activity matches the tool calls an agent reports, but it is not a framework for observability. In its place, the RFC now describes the layers monitoring can observe and what each costs:

| Layer | What it shows | Cost and difficulty |
|-------|---------------|---------------------|
| Reasoning content | Intent that actions can hide | Very noisy and varies between runs. Sample a small share of runs, or read it only after another signal fires |
| Tool calls and their results | Which tool, its arguments, its result, how often | Cheapest and structured. The record comes from the agent's own runtime, so it can miss what a tool does beyond the logged call |
| Kernel level | File, process and network activity | Shows what actually happened, which complements tool-call records. More expensive, and has to be matched back to the agent and tool call |

**To discuss:**

1. Is detection and alerting the right boundary, with response mapped to the controls listed in the RFC?
2. The different kinds of logs, and how each is useful. Should the RFC name a minimum signal set, for example every tool call, kernel-level events for tools that can act beyond their logged call, and a sample of reasoning?
3. The §6.2 position from September 1–14 in **#197** still says the control includes "a response path" and "is fail-closed". If the group agrees with the rework, that position needs updating.
